# 0003 — Production Threat Model and Trust Boundaries

- **Status:** Accepted
- **Date:** 2026-07-15
- **Milestone:** 20 — Pre-Audit Production Design
- **Implementation status:** Not implemented; this ADR defines the target design

## Context

The prototype validates its current instruction accounts, but it does not yet state
which surrounding systems are trusted, what each privileged role may do, or which
failures the production design must tolerate. A frontend, SDK, RPC response, token
issuer, or correctly signed governance transaction can still be malicious or wrong.
The on-chain program must remain the final security boundary.

OWASP's Smart Contract Security Verification Standard is primarily written for EVM
contracts. Its architecture, governance, authorization, external-interaction,
arithmetic, and denial-of-service principles are adopted here where they map to
Solana; EVM-specific proxy and Solidity mechanics are not applied mechanically.

## Decision

### Protected assets and properties

The production design protects:

- tokens represented by `VaultState.total_assets`;
- the integrity of `total_assets`, `total_shares`, and every user share balance;
- users' ability to exit whenever the withdrawal path is not itself unsafe;
- vault, mint, custody, token-program, PDA, and account-version identity;
- pause, configuration, treasury, and upgrade authorities;
- release provenance, monitoring evidence, and incident records.

Availability is a security property. An attacker or compromised authority must not be
able to convert an ordinary operational incident into indefinite user lockout.

### Trust boundaries

| Actor or dependency | Trust decision | Required control |
|---|---|---|
| User | Untrusted | Validate signer, PDA, owner, mint, token account, amount, position, version, and state transition on-chain. |
| Frontend | Untrusted convenience layer | Pin cluster, program ID, mint, and token-program ID; never hold privileged keys; never substitute for on-chain authorization. |
| SDK | Untrusted transaction constructor | Program revalidates every account and argument. Generated bytes and decoders receive independent tests. |
| RPC provider | Untrusted for correctness and availability | Use private primary and independent fallback providers; treat reads as advisory; monitor divergence and confirmation failures. |
| Solana runtime | Trusted platform dependency | Document supported cluster and confirmation/finality policy; monitor platform incidents. |
| Legacy SPL Token Program | Pinned external program dependency | Accept only `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`; constrain all token accounts and CPIs. |
| Token mint/issuer | External counterparty risk | Governance allowlists each mint; reject a live freeze authority and revoke mint authority for the initial launch; document the resulting fixed supply. |
| Pause council | Trusted only for bounded emergency actions | May enter exit-only mode and lower exposure; cannot transfer custody, upgrade, recover excess, or increase caps. |
| Protocol governance | Trusted for reviewed configuration | May approve mints, raise caps, authorize recovery, and configure exceptional full pause through multisig policy. |
| Upgrade council | Trusted for program-loader upgrades | Separate 3-of-5 multisig/timelock policy; no individual key controls upgrades. |
| Treasury | Trusted only as a destination | Deterministic same-mint destination for approved excess recovery; no custody authority. |
| Operations and incident commander | Untrusted for on-chain authorization | May monitor, alert, classify, prepare transactions, and coordinate; cannot execute privileged action alone. |

The same humans may serve in more than one council, but each role uses a distinct
address, policy, and signer threshold. Loss or compromise of one role must not
automatically grant every other role.

### Transaction and data assumptions

- A signature proves control of a key, not that the requested state transition is safe.
- Account order, UI labels, token symbols, and RPC-provided metadata confer no authority.
- Replayed, duplicated, reordered, expired, and concurrently submitted transactions are
  expected conditions.
- Direct token transfers into custody are expected and do not alter internal accounting.
- Unknown account versions, unknown token programs, and unapproved mints fail closed.
- Frontend hiding or disabling a control is never an authorization mechanism.
- Events are monitoring evidence, not consensus or authorization inputs.

### RPC and signing operations

- Production uses a private RPC endpoint with an independently operated fallback.
- Privileged signing happens outside the frontend and general-purpose CI.
- Devnet and mainnet use separate program IDs, deployment authorities, wallets,
  configuration, and RPC credentials.
- Transaction construction uses fresh blockhashes, explicit expiry handling, bounded
  retries, priority-fee policy, and appropriate confirmation/finality.
- No seed phrase, private key, keypair JSON, private RPC URL, or multisig recovery
  material is committed or printed in logs.

## Alternatives considered

**Treat the official frontend and SDK as trusted security boundaries.** Rejected:
clients can be modified, compromised, bypassed, or replaced.

**Trust one RPC response.** Rejected: RPC providers can be stale, censored,
rate-limited, inconsistent, or unavailable without changing on-chain truth.

**Use one administrative key for pause, configuration, upgrade, and treasury.**
Rejected: it creates a single compromise path to every privileged capability and
violates least privilege and separation of duties.

**Support arbitrary token programs and mints.** Rejected for the initial launch: it
expands external-call and token-behavior risk beyond what the current program and tests
cover.

## Consequences

- Every future implementation milestone must identify which boundary it changes and
  add negative tests for account and authority substitution.
- RPC redundancy, multisig membership, signing operations, and key backup require human
  operational work; they cannot be completed solely in repository code.
- Token-2022, a new mint class, a new external program, or a new privileged role
  requires a new or superseding ADR before implementation.
- The repository remains a non-production prototype until all launch gates in ADR 0009
  are met.
